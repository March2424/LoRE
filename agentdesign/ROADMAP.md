# 游戏本地化 Agent 工作台实现路线图

本路线图以 `submission/agentdesign/` 为后续工作目录。首版面向本地化编辑，选择 Naev 的一个 Gettext PO 资源子集做英译中。用户可以导入资源、通过自然语言下达任务、查看 Agent 的取证过程、处理未决项，最终导出能由游戏工具链加载的 PO 文件。随后补齐术语变更与反馈迭代。

## 现有基础与实现顺序

- 复用研究提交包中的资源适配、源侧实体图、SQLite 记忆、作用域检索和候选选择协议。提交包的快速验证以 CSV 为入口，产品所需的原生 PO 导入和回写在本路线中验收。[研究提交包](../game-localization-agent/README.md) · [Naev 数据说明](../game-localization-agent/docs/NAEV_DATA.md)
- [PR #8](https://github.com/March2424/LLM_Project/pull/8) 提供 LangGraph 审校修复、选择性修订和本机演示。产品接入时将模型服务统一到 DeepSeek，将 Reviewer 的具体查询接入源图、术语和译例检索。
- 主线依次为 **Pi 与 DeepSeek 接入 → 主动取证 → 后端任务与前端交付 → 术语维护 → 反馈迭代**。Pi 是首版必接组件，从 P0 进入真实模型链路。P3 通过后可交付首个可用版本，P4 和 P5 分别验收维护与反馈闭环。已完成 P0 翻译、P1 主动取证和 P2 本地任务服务，见 [P0](docs/P0.md)、[P1](docs/P1.md) 与 [P2](docs/P2.md) 验收记录。[P3](docs/P3.md) 已实现简易工作台与原生 PO 交付。[P4](docs/P4.md) 已实现术语维护。P5 待实施。

## 运行时分工与模型配置

前端请求进入 Python API。Python + LangGraph 管理任务状态、权限、快照、预算、提交与恢复。服务端 Node 进程通过 `@earendil-works/pi-agent-core` 提供意图识别和 Reviewer 运行时。意图识别由 Pi 发起一次结构化模型请求，Python 校验目标与权限。Reviewer 在 Pi 内运行「选择工具 → 执行 → 观察结果 → 给出结论」的循环，实际领域工具仍调用 Python。Pi 把判定和工具回执交回 LangGraph，提交、版本变更和人工等待由任务工作流处理。[Pi Agent Core](https://github.com/earendil-works/pi/tree/main/packages/agent)

所有需要模型的节点统一使用 DeepSeek `deepseek-v4.1-flash-1017`，包括意图识别、上下文选择、翻译、Reviewer、修复，以及需要模型的知识提取和反馈候选生成。Pi 使用同一 Responses provider，Python 的单次模型调用通过共用的后端模型接口接入。各角色独立管理提示词、输出协议和调用预算。

| 配置 | 值 |
| --- | --- |
| 协议 | OpenAI 兼容 Responses API，调用 `responses.create` |
| Base URL | `https://tokendance.space/gateway/v1` |
| 模型 ID | `deepseek-v4.1-flash-1017` |
| 凭据 | 服务端环境变量 `DEEPSEEK_API_KEY`，配置样例使用占位符 |

P0 先验证网关的普通响应，再验证 Pi 所需的结构化输出、流式事件和「工具请求 → 工具结果 → 模型续答」。Pi 官方支持自定义 OpenAI Responses provider，网关具体行为以实测为准。若网关只支持普通 Responses 输出，由 provider 适配层把返回文本中的结构化工具动作转换为 Pi 的工具请求事件，再由 Pi 调用工具并继续循环。模型和网关沿用上述配置。[Pi 自定义 Provider](https://docs.pi.dev/latest/custom-provider)

| 阶段 | 交付物 | 验收证据 |
| --- | --- | --- |
| P0 云端集成 | Pi + DeepSeek 的 M5 入口 | Naev 小批量记录包含 DeepSeek 选择动作、Pi 审校结果和译文版本 |
| P1 主动取证 | Pi Reviewer 与首批只读工具 | 一例因新证据完成修复，一例证据不足进入人工接手 |
| P2 任务服务 | 意图路由、任务状态、暂停恢复及进度 API | 刷新或重启后恢复原任务，重复请求只产生一次有效写入 |
| P3 前端与 PO | 上传、工作台、复核和下载完整流程 | 导出的真实 PO 可重新解析并通过 Naev 工具链验证 |
| P4 术语维护 | 只读预演、确认应用和回滚 | 内外作用域、已满足规则、锁定及版本冲突都有明确结果 |
| P5 反馈迭代 | Prompt、Memory、Skill、Harness 的候选变更与轨迹回放 | 固定模型，对现行和候选策略做同条件回放，记录指标及发布决定 |

## P0 · 接通云端翻译闭环

入口、固定清单和逐条验收见 [P0 验收记录](docs/P0.md)。

- [x] 以本地研究提交包和 Naev SQLite 源图为基线，在独立运行目录核对 PR #8 接口，登记输入、快照、源库哈希和依赖版本。检索和译文提交在本机运行，模型请求通过 DeepSeek Responses 网关执行。
- [x] 配置 DeepSeek Responses provider，按用户提供的 `responses.create(model=..., input=...)` 验证单次请求，再接通 Pi Reviewer。记录输出结构、网关返回的用量及失败类型。资源文本与审校证据从服务端按当前任务范围发送给网关。
- [x] 用 DeepSeek 接入 M5 的 `selector` 接口。生成有序候选 ID 并复用候选校验、硬规则保留及预算打包。服务端以适合 DeepSeek 的计数或保守估算执行业务预算，网关用量单独记录。选择输出无效时回退到固定排序，并保存原因。
- [x] 从命令行跑通「检索 → DeepSeek 选择 → 草译 → 硬检查 → Pi Reviewer → 必要时修复并复审 → 提交」。固定小样本清单，包含正常译文、占位符错误、同名歧义及缺证据。先离线核对接口，再用指定网关试跑，记录 Reviewer 的结构失败、漏判、误判及耗时。

**验收。** 保存一次真实运行的样本 ID、候选池、实际 ContextPack、DeepSeek 选择结果、Pi 审校回执、调用与版本记录。审校失败项保留原因，未通过的草稿不得写成批准译例。

## P1 · 让 Reviewer 主动取证

只读源图工具和两条真实用例已验收，见 [P1 验收记录](docs/P1.md)。

- [x] 在 Pi 上注册具名 Reviewer 工具，并校验最终判定 `pass`、`repair` 或 `needs_human`。Reviewer 在判定前可发起工具调用，携带问题类别、目标实体或资源线索。项目 ID、作用域、快照与读水位由 Python 工具服务绑定。
- [x] 先接 `search_source_graph`，允许按实体、关系或资源线索查询。工具返回证据 ID、版本、出处及相关片段，并记录未命中或越界拒绝。首版每条资源最多一次主动补查，另外记录调用和 token 预算。
- [x] 拿到有效新证据后重新打包。修复后的译文与新的输入包重新校验和审校。没有新证据、证据冲突或预算耗尽时，生成带原因的人工复核项。禁止通过重复调用同一查询伪造进展。
- [x] Pi Reviewer 已注册 `lookup_glossary`、`search_tm`、`get_character_note`。三者沿用源图工具的单次查询预算，只读批准且在当前任务快照可见的记忆。新增三项已完成离线桥接验证，真实网关复验待做。

| 模块 | 工具或服务动作 | 当前入口 |
| --- | --- | --- |
| M1 数据 | `inspect_resource`、`get_source_occurrence`、`validate_export` | 资源与上传目录 API、后端源库读取、PO 预览校验。Pi 可通过 `search_source_graph` 的 `resource` 查询读取授权源记录。 |
| M2 记忆 | `lookup_glossary`、`search_tm`、`get_character_note` | 三项均为 Pi Reviewer 只读工具。人工批准和提交仍走后端。 |
| M3 检索 | `search_source_graph`、`get_evidence` | 两项均为 Pi 只读工具。`get_evidence` 按完整带版本的 ID 查看授权证据，工作台也可通过条目 `/evidence` API 查看轨迹。 |
| M4 选择 | `select_context` | LangGraph 选择节点调用 DeepSeek，后端校验候选 ID。 |
| M5 翻译与审校 | `translate_item`、`check_constraints`、`repair_item` | LangGraph 翻译、硬检查、修复及审校节点。 |
| M6 维护 | `plan_update`、`get_translation_diff`、`apply_update`、`rollback_version` | 术语预览和差异由 `/maintenance` API 提供。应用、术语回滚和译文版本回滚由编辑显式触发。 |
| M7 评测 | `run_replay_eval`、`compare_configs` | P5 `/policy/candidates/{id}/replay` 提供历史回放和双配置对比。通用质量评测属于研究流程。 |

当前领域工具注册入口是 [Pi Reviewer](pi/reviewer.mjs)。P2 支持等待补充和人工复核时暂停，并能从检查点继续。运行途中由编辑主动暂停并插入指令尚无独立入口。P3 的游戏内 PO 加载、P4 的真实网关术语维护质量、P5 的真实模型策略对照仍待验收。

**验收。** 在同名不同分支的案例中，轨迹应显示 Reviewer 发出的具体查询、初始包里没有的新证据及修订前后差异。再验证无命中时进入人工复核，且另一分支的信息未进入实际输入。工具调用应改变工作流所见事实，前端展示记录和依据即可。

## P2 · 意图、任务状态和 API

入口、操作约定与实际验收见 [P2 验收记录](docs/P2.md)。

- [x] 支持五种首版意图。结构化按钮可直接送出已知意图；自由文本由 Pi 使用 DeepSeek 返回一次结构化识别结果，包含意图、目标、限制及缺失信息。Python 解析真实资源 ID，复用前端当前选中的项目、文件或分支。缺语言、资源名有歧义时返回待补充信息，收到答案后继续原请求。
- [x] 复合请求用有依赖关系的步骤表达，例如「翻译 → 审校通过 → 导出」。取消、重试、批准、锁定和回滚由明确的 API 动作触发。
- [x] 后端持久化任务和条目结果。任务使用 `queued`、`running`、`awaiting_input`、`awaiting_review`、`completed`、`partial`、`failed`、`cancelled`。条目另记通过或已提交、无须修改、已锁定、证据不足、版本冲突和执行失败。仍需编辑接手的任务保留为待复核。用户接受已完成部分并关闭剩余项后，再标为 `partial`。
- [x] 补齐 LangGraph 的暂停和恢复，保存可恢复的任务标识、源与知识快照、预算和已完成调用。超时可按策略重试，版本冲突要求重新预演，外部请求结果未知时先核对调用账本。写入校验人工锁与预期版本，重复操作用幂等标识去重。
- [x] 推荐 FastAPI、已有 SQLite 和一个后台 worker 起步。任务接口提供创建、详情、继续、取消、条目复核和文件下载。结果统一返回 `status`、`reason`、`job_id`、`artifacts`、`evidence_refs`、`next_actions`。SSE 推送阶段及条目变化，页面重连先恢复服务端状态与事件位置。

| 意图 | 后端出口 |
| --- | --- |
| `translate` | 翻译任务、通过的译文和待复核项 |
| `review` | 逐条问题、证据和修订建议 |
| `propose_update` | 绑定版本的影响清单和差异，完整应用在 P4 启用 |
| `explain` | 依据该译文版本实际收到的输入和审校回执回答 |
| `export` | 可下载的已批准译文 JSON、版本校验和排除项。原生 PO 在 P3 交付。 |

**验收。** 用三条交互核对任务链路。资源不明确时能继续补充；刷新页面或重启 worker 后能恢复待复核任务；重复点击批准不会产生额外译文版本。前端显示的终态、可执行动作和导出数量以服务端状态为准。[LangGraph 中断与恢复](https://docs.langchain.com/oss/python/langgraph/interrupts)

## P3 · 前端与原生 PO 交付

入口、范围与实际验收见 [P3 验收记录](docs/P3.md)。

- [x] 完成 PO 往返。解析资源身份 `(msgctxt, msgid, msgid_plural)` 并映射稳定 occurrence ID。保留复数槽位、换行、占位符、游戏控制标记和非目标记录。多个出现位置共享同一个 PO 键而译文不一致时，列为导出冲突供编辑选择。用固定快照的小子集先验证。
- [x] 用 React 和 TypeScript 做四个必需视图。资源页负责上传和选择范围；工作台显示计划、实时进度、工具依据与中途结果；复核页并排显示原文、草稿、问题和证据；交付页提供格式校验、下载及排除清单。复核编辑后重新执行硬检查。
- [x] 前端使用同一套任务 API。任务卡片显示已处理、可导出、待复核、锁定或失败数量，提供下一步按钮。证据面板能打开 ID 对应的来源并区分召回内容和模型实际输入。部分导出需要列明排除原因，保留源目录中的其他条目。

**首版交付验收。** 一个编辑从浏览器上传真实 Naev PO，选择一组资源下达翻译任务，打开一条主动取证记录，处理至少一个待复核项，再下载 PO 和变更报告。用 `msgfmt --check` 等 Gettext 校验及 Naev 对应工具链验证产物。仅完成程序校验时，验收记录写明实际覆盖。

工作台另支持粘贴文本进行中译英或英译中，复用审校、占位符检查、版本和 JSON 导出。[任务入口与验证](docs/P2.md#双向文本任务)

## P4 · 术语变更与版本管理

操作范围和验收见 [P4 验收记录](docs/P4.md)。

- [x] 复用 M6 的依赖、作用域和检索发现逻辑，预演覆盖旧、新作用域。预演计算影响清单和拟改 diff，包含已满足现行规则、需复核、已锁定和证据不足等结果。预演过程不发布术语或译文版本。
- [x] 应用时核对计划绑定的知识和译文版本，并对直接及级联写入检查人工锁。先判断旧译文是否已满足规则，仅对确实需改或需要复核的项运行模型，并记录 `no_change` 与未决项。
- [x] 前端提供术语变更、预演、确认应用及回滚入口，显示每条受影响译文的原因、前后版本和调用数。回滚追加新版本并保留审计。

**验收。** 一次术语变更覆盖一条应改、一条已满足、一条范围外和一条锁定记录。预演前后业务库版本一致；应用只产生预期改动；并发版本变化能阻止旧计划写入；回滚能找回历史译文。

## P5 · 反馈驱动的改进与历史轨迹回放

保持执行模型权重固定，通过更新 **Prompt、Memory、Skill 和 Harness** 改善后续任务表现。改进链路为「收集反馈 → 找出重复成功或失败 → 生成候选改动 → 历史轨迹回放 → 独立用例复验 → 发布或保留现行版本」。

首版入口、范围和验证结果见 [P5 验收记录](docs/P5.md)。

| 可更新组件 | 反馈如何转成可运行的改动 |
| --- | --- |
| **Prompt 与回答模板** | 把多次验证有效的约束写进适用角色的 Prompt。可调整 Reviewer 的问题描述、证据引用和转人工模板，也可调整用户看到的任务摘要与回答模板。业务硬规则仍以批准数据和程序检查为准，任务状态和统计取后端结果。 |
| **Memory** | 用户更新术语、人物设定或项目事实后，保存内容、来源、作用域及版本。单条人工改译保留为反馈与译例候选；明确的项目级更新走批准流程，相关旧条目按规则失效。 |
| **Skill** | 将重复成功的流程整理为版本化 Skill，写清触发条件、所需输入、工具步骤、预期产物和转人工条件。例如把“同名物品 → 限定分支查源图 → 比对批准术语 → 修复并复审”固化成可复用步骤。 |
| **Harness** | 对重复出现的失败调整工具接口、参数约束与检查。支持按实体、别名或资源线索做查询扩展，并逐项调整候选数、图跳数、词法与图召回排序、软证据预算。扩展后的查询仍经过现有作用域和快照校验。 |

- [x] P0 / P1 命令行保留批次轨迹。P5 将人工改前改后与原因关联到 P2+ 工作台任务、资源版本、快照与策略版本，复用已保存的模型调用、Pi 工具回执、ContextPack 和审校结果。
- [x] **记录回放**复用历史工具和审校回执，对照转人工模板并重新执行硬检查。**策略对照**固定历史草稿、初始输入包和范围，重跑只读源图查询，可选用同一历史模型重新执行首次 Pi 审校。两种模式均使用临时 SQLite 副本。
- [x] 反馈样本与独立验证样本按 occurrence ID 和原生文件隔离。报告证据命中、缺口解决、作用域违规、硬规则问题、转人工和实际调用用量。Memory 候选在历史包上叠加 P4 术语预览。
- [x] 候选保留组件版本、逐条差异、人工发布或保留决定及回滚记录。通过发布闸门的策略由后续任务冻结使用。[Agent 评测设计](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [ ] 使用真实网关重跑候选策略的首次 Pi 审校，结合独立用例的人工判断验证语义效果。后续可扩展检索排序和其他 Skill 流程。

**验收。** 使用同一 DeepSeek 模型，在一批历史轨迹上比较当前策略和候选策略。至少完成一项查询扩展或召回参数的重跑，以及一次回答模板或检查逻辑的记录回放。交付逐条差异、未通过用例和发布决定，并复验作用域、人工锁与硬约束。产品结论来自自动运行输出与实际人工复核，历史上传修订稿重评分单列。[项目评测与版本说明](../../docs/PAPER_PROJECT_OVERVIEW_20261117.md)
